# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Added
- **Mark a recipe as made before, with a matching filter** (WISH-0091). New `Recipe.hasBeenMade` flag, toggled via a check-circle icon on the recipe detail page's AppBar (green when set) — deliberately a quick action outside the edit form, the same pattern as the existing favorite heart, so it's not part of the autosave/dirty-check snapshot. A matching AppBar filter toggle on the recipe list (alongside the existing WIP-only and favorites-only filters) narrows the list to made-before recipes via a new `recipeMadeOnlyProvider`. Recipe list cards also show a small green check-circle next to the title when set, mirroring how WISH-0089 surfaced inventory's `isOpened` flag. 4 new model tests cover the default-false behaviour, toMap/fromMap roundtrip, legacy-data tolerance, and independence from other fields
- **Pull-to-refresh on every data list, including via mouse drag on web/desktop** (WISH-0090). All 13 CRUD list pages — inventory, catalog, recipes, knowledge, passwords, contacts, conversations, feedback, files, tasks, shopping, and both finance lists (transactions, assets) — are now wrapped in a `RefreshIndicator` whose `onRefresh` does `ref.refresh(xListProvider.future)`: since every one of these is a `StreamNotifierProvider` (IMPR-0018), refreshing tears down and re-establishes the Firestore snapshot listener, which is a meaningful "reload" even for already-live data (recovers from a stuck listener, forces a check against the server instead of the local cache). A new shared `PullableCenter` widget (`lib/presentation/widgets/pullable_center.dart`) makes the loading/empty/error placeholder states pullable too — `RefreshIndicator` only ever fires from an actual `Scrollable`, so a bare centered message couldn't be dragged at all without it — and every list's `ListView` got `physics: AlwaysScrollableScrollPhysics()` so the gesture works even when there's too little content to scroll on its own. Separately, and this is the part that made "on web/desktop" not work at all before: Flutter's default `ScrollBehavior` excludes `PointerDeviceKind.mouse` from the devices allowed to drag-scroll (only touch/stylus/trackpad do), so a mouse click-drag couldn't produce the overscroll `RefreshIndicator` listens for in the first place — no amount of wrapping would have helped. `AppScrollBehavior` (`lib/presentation/theme/app_scroll_behavior.dart`) adds mouse to `dragDevices` and is set app-wide via `scrollBehavior:` on `MaterialApp.router`. Deliberately out of scope: the Calendar page (a grid + agenda, not a pullable list), the WIP overview (a synchronous recompute over other providers already covered on their own pages, with no stream of its own to refresh), and the People directory (built on a raw `StreamBuilder` rather than the app's provider pattern — retrofitting it just for this felt like a disproportionate detour). 4 new tests: `AppScrollBehavior` exposes mouse in `dragDevices` and an end-to-end mouse-drag actually triggers `onRefresh`; `PullableCenter` renders its child and stays pullable even with tiny content

### Fixed
- **Search fields went blank (but stayed applied) after navigating away and back** (BUG-0047). All six search fields (inventory, catalog, recipes, knowledge, passwords, contacts) read/wrote a Riverpod `StateProvider<String>` but bound the `TextField` with no `controller`, so the box showed whatever Flutter's own implicit controller happened to hold — which could go blank or stale independently of the provider still silently filtering the list. New `useSyncedSearchController` hook (`lib/presentation/hooks/use_synced_search_controller.dart`) keeps the visible text pinned to the provider's value always, fixing the mismatch regardless of cause. Separately, per the wish in the report, search now behaves differently depending on where you navigate: pushing into a detail/edit page and popping back keeps the search (unchanged, since that's a normal push/pop within the same route and never disposes the list page); switching to a genuinely different feature now resets it. Inventory/Recipes/Knowledge live inside the bottom-nav's `IndexedStack` shell, which never disposes an inactive tab, so `AppShell` now resets the search of whichever shell-branch tab you're leaving whenever the active branch index changes. Catalog/Passwords/Contacts sit outside the shell as plain pushed routes that already get disposed when you leave for elsewhere, so they reset their own search on a fresh mount. 4 new widget tests cover the hook (initial seed, external resync, not fighting live typing, cursor placement). The `AppShell` branch-index reset logic and the six pages' live cross-feature behaviour were verified by code review and the full test suite — no UI automation tool was available in this environment to click through the running app interactively

### Added
- **Opened status** for inventory items (WISH-0089). A new `isOpened` flag, independent of the existing fill-percentage tracker (WISH-0078) — the user wanted a simple opened/in-use checkmark for items where tracking exact fullness is overkill. Toggle it via a "Opened" checkbox on the item edit page; opened items get a small check-circle icon next to their name in the list and "Opened" appended to the subtitle line. Carried over when splitting an item into a new one via transfer-to-new-item (WISH-0088), same as fill percentage. Five new model tests cover the default-false behaviour, toMap/fromMap roundtrip, legacy-data tolerance, copyWith, and independence from `fillPercent`

### Changed
- Removed the app module's explicit `id("kotlin-android")` from `android/app/build.gradle.kts` so it now picks up Kotlin via Flutter's Built-in Kotlin support instead of the standalone Kotlin Gradle Plugin (IMPR-0022) — verified with clean debug and release Android builds. This clears the "app project applies KGP" half of Flutter's build warning; the other half (8 plugins — `device_info_plus`, `file_picker`, `firebase_storage`, `home_widget`, `package_info_plus`, `photo_manager`, `share_plus`, `wakelock_plus` — still applying KGP themselves) is investigated but **not yet fixable**: `wakelock_plus`/`firebase_storage`/`home_widget`/`photo_manager` have no upstream fix at any released version, and `device_info_plus`/`package_info_plus`/`share_plus`/`file_picker` are coupled into a single win32-version cluster whose only unblocking release is a `file_picker` prerelease that (tested directly) doesn't even clear the warning and hit real compile errors — not worth pinning a beta for. `android.builtInKotlin`/`android.newDsl` in `gradle.properties` are deliberately left untouched; testing showed they have no effect while AGP is pinned to 8.11.1 and the real failure trigger is AGP 9, a separate future migration. Full investigation, per-plugin blocker table, and revisit conditions recorded in `docs/decisions/ADR_005_kgp_builtin_kotlin_migration.md`
- Migrated the discontinued `flutter_markdown` (0.7.7) to its maintained fork `flutter_markdown_plus` (1.0.12) (IMPR-0015). Three files render markdown — the knowledge view page, the knowledge editor's live preview, and the Gemini chat page — and all of them use only `MarkdownBody(data:, selectable:, onTapLink:)`, which the fork keeps API-identical, so the swap was a dependency change plus three import lines. No behaviour change; analyzer clean and all 253 tests pass
- Extracted the duplicated autosave machinery into a shared `useAutosave` hook (IMPR-0020) at `lib/presentation/hooks/use_autosave.dart` — the first custom hook, per the flutter_hooks house style. Recipe and knowledge edit pages both hand-rolled the identical stack: `Timer.periodic` from `settings.autosaveIntervalMinutes`, snapshot comparison to skip no-op saves, the BUG-0033 browser-throttle guard (skip ticks within 80% of the interval — previously copy-pasted verbatim in both files), `_lastAutosaveAt`/`_lastSavedSnapshot` bookkeeping, and the "Auto-saved" snackbar. The hook takes a `snapshot()` and a `save()` callback (returning false to skip, e.g. on validation failure) and returns an `AutosaveController` that also carries the dirty-check baseline the WISH-0079 unsaved-changes guard reads (`isDirty`/`markClean`), since autosave and the guard share one "last saved snapshot". Both pages became `StatefulHookConsumerWidget`s (superclass swap only) and dropped ~60 lines each; any future edit page gets autosave in one hook call. Differences preserved: recipes only autosave existing recipes (`enabled: _isEditing`); knowledge autosaves new pages too, creating the page on the first tick. The throttle guard now reads `clock.now()` (new direct dependency on the already-transitive `package:clock`) so it's fake-time testable — identical behaviour in production. 8 widget tests cover baseline capture, dirty tracking, tick-saves + snackbar, no-op skip, the BUG-0033 throttle window, save-returning-false, error swallowing, and the disabled/zero-interval cases
- Extracted the shared image-attachment choreography out of the edit pages (IMPR-0019). Five pages (recipe, inventory, catalog, calendar event, task) hand-rolled the same trio of `_savedImageUrls` + `_pendingImages` + `_removedImageUrls` fields, the upload-pending-on-save and delete-removed-from-Storage-on-save loops, and a thumbnail strip with remove overlays — any fix meant the same change in five places. Now a single `ImageAttachmentController` (`lib/services/image_attachment_controller.dart`, a `ChangeNotifier`) owns the three buckets, the save-time `uploadPending`/`deleteRemoved` phases (with a `deletable` filter hook so inventory's WISH-0088 shared-image guard still applies), and the dirty signature used by the unsaved-changes snapshots; a shared `ImageAttachmentStrip` widget renders the strip (fullscreen-preview tap by default, set-primary tap + Primary badge for recipes via `showPrimaryBadge`/`onTapImage`); and `pickImageInto`/`addImageFromSource` (`lib/presentation/widgets/image_attachment_picker.dart`) hold the source-sheet → resolve → preview/crop → append flow that was byte-identical across four pages. `RecipeImagesSection` (IMPR-0009) was absorbed into the shared strip and deleted. Behaviour notes: catalog's image wrap-grid became the same horizontal strip as the other pages (and keeps its gallery/clipboard-only sheet), and removing an image before the primary no longer shifts which image is marked primary — the index now follows its image (previously it silently pointed at the next one). Knowledge is deliberately untouched: its attachments are name+URL objects uploaded immediately via `deleteFile`, a different choreography that would have distorted the shared API. 12 new unit tests cover the controller's index math, primary-index follow/clamp, upload/delete phases, the deletable filter, and listener notifications
- Extended stream-based loading (the IMPR-0016 inventory/catalog pattern) to the remaining 11 list features (IMPR-0018): tasks, shopping, recipes, knowledge, calendar, contacts, conversations, feedback, files, finances, and passwords/vault. Every service gained a `watch*()` stream (Firestore `collection.snapshots()` mapped to sorted model lists; mock services emit via a broadcast controller on every save, closed through `ref.onDispose`) and all 13 list notifiers became `StreamNotifier`s, removing 45 `ref.invalidateSelf()` calls — mutations now cost single-document reads instead of re-downloading the whole collection, and edits sync live across devices. Special cases: **calendar** keeps its task/finance-derived event merge by mapping the custom-events stream against the watched task/transaction lists (Google sync, the `_syncing` re-entry guard, and the auto-sync cooldown are untouched); **feedback** combines its public + private collections with a manual combine-latest that emits only once both snapshots have arrived; **finances** streams all three sub-collections (transactions, categories, assets) with the category-seeding behaviour preserved by seeding before the first snapshot subscription; **vault** streams *encrypted* entries only — decryption happens inside the notifier's stream map keyed on the in-memory unlock key, and locking rebuilds the provider to an empty stream so plaintext never outlives the unlock session. 14 new unit tests in `test/service_watch_streams_test.dart` lock the emit-on-listen / emit-per-mutation contract for every converted mock service
- Thumbnails now decode at display size instead of full resolution (IMPR-0017). Uploads are stored at up to 1920px, but list tiles and edit-page image strips render them at 40–120 logical px — without a decode cap each visible thumbnail held a full ~1920px bitmap (~8MB RAM apiece), which meant scroll jank and image-cache thrashing as inventory/catalog grow into hundreds of image rows. Added `memCacheWidth` (3× logical width for device-pixel-ratio headroom) to all 14 fixed-size `CachedNetworkImage` call sites: inventory/catalog/shopping list tiles and catalog pickers (40px→120), recipe list tile (56px→168), recipe images strip (80px→240), inventory/catalog/calendar/task edit strips (100px→300), and feedback/conversation edit strips (120px→360). Full-screen viewer and detail-page galleries intentionally keep full-resolution decoding
- Inventory and catalog lists now load via Firestore realtime streams instead of one-shot full fetches (IMPR-0016). Both services gained `watchItems()` (`collection.snapshots()` mapped to sorted model lists; the mock services emit via a broadcast controller on every save) and `InventoryListNotifier` / `CatalogListNotifier` became `StreamNotifier`s. The big win: every add/update/delete previously called `ref.invalidateSelf()`, re-downloading the **entire** collection per mutation (500 items = 500 reads per save) — now the initial subscription reads the collection once and Firestore pushes only deltas, so mutations cost single-document reads, the UI updates instantly via latency compensation, and edits sync live across devices. All derived providers (filtered/search/sort, categories, locations, total value) are unchanged since `StreamNotifierProvider` exposes the same `AsyncValue<List<T>>` shape. Six new unit tests lock the `watchItems()` contract (initial emission, emission per mutation, sort order) via `InMemorySharedPreferencesAsync`; `shared_preferences_platform_interface` added as a dev dependency for that

### Fixed
- **Expiry notifications were never sent** (BUG-0046). Two bugs in `functions/src/notifications.ts`: (1) the daily check queried `users/{uid}/inventoryItems` while the app stores items in `users/{uid}/inventory`, so the query always returned empty and no user ever received an expiry reminder; (2) stale-token cleanup called `FieldValue.arrayRemove(invalidTokens)` with an array argument — Firestore rejects nested arrays — so the first user with a dead FCM token would crash the whole run (fixed to spread varargs: `arrayRemove(...invalidTokens)`). Also added a summary log line to the scheduled handler (`Expiry check: N users checked, M notifications sent.`) — the function previously logged nothing, which is why the bug went unnoticed since the feature shipped. Verified in production: force-ran the scheduler job, log shows `3 users checked, 1 notifications sent`, a real push was delivered for an item expiring tomorrow, and 2 stale tokens were pruned without error

### Changed
- List subtitles and detail metadata now show the last-updated time instead of the created time so users see when an item was actually last touched, not just when it first appeared (WISH-0073). Specifically: conversation list tiles, feedback list tiles, and the catalog detail metadata line now use `updatedAt`. The catalog detail line shows `Updated X · created Y` when the two timestamps materially differ (≥ 1 minute), or just `Created X` when nothing has been edited yet. ### Added
- **Transfer to a new item on the go** (WISH-0088). The inventory transfer dialog's "To" picker gained a "➕ New item at another location…" option: instead of picking an existing destination, enter a location and the transferred amount is split off into a brand-new item created on the spot — a copy of the source's data (name, description, category, price, purchase/expiry dates, **image references**, barcode, catalog link, fill percentage, nicknames) with the new location and the transferred quantity, while the source's quantity is decreased. Since two items can now reference the same Storage image, both image cascade-delete paths (item delete, and removing an image on the edit page) filter through a new `imageUrlsSafeToDelete` guard that skips URLs another item still references — deleting either copy no longer breaks the other's pictures. In this mode the amount must be strictly positive (a not-yet-existing item has nothing to give back) and can drain the source to exactly zero but not below; validation runs live in the dialog and is re-checked in the new `InventoryListNotifier.transferToNewItem` against fresh data. The outcome preview adapts ("Pasta: 5 → 3 · New item at Storage: 2"). Ten new unit tests: five for `validateTransferToNew` (normal split, drain-to-zero, zero/negative rejection, overdraw rejection) and five for the shared-image guard (unshared deletes, sibling-protected keeps, self-reference doesn't protect, null exclude id, empty candidates)
- **Daily agenda notification at 06:00 Amsterdam time** (WISH-0087). A new scheduled Cloud Function (`dailyAgendaNotification`, cron `0 6 * * *` in `Europe/Amsterdam` so CET/CEST is handled automatically) sends each user a morning push summarising the tasks due today and today's calendar events from the app's own data — events that exist only in Google Calendar are not in Firestore and are therefore excluded, and locally-stored events of type `googleCalendar` are filtered out as well. Title reads like "Today: 3 tasks, 2 events" with the names in the body. Users with nothing due and no events get no notification; users with notifications disabled or no registered devices are skipped. Multi-day events that span today are included, not just ones starting today, and completed tasks are excluded. Invalid FCM tokens are pruned the same way the expiry reminder does. Admins get a "Force daily agenda" action in Admin → Notifications (backed by a new `triggerDailyAgenda` admin-only callable) mirroring "Force expiry check", and the two admin trigger calls now share one plumbing helper in `AdminService`. Both functions deployed to `europe-west4` and verified healthy
- **Sort inventory by expiry date** (WISH-0085). A new sort menu (sort icon) in the inventory AppBar offers "Name" and "Expires soonest" — the latter floats the items to eat/drink first to the top. Items without an expiry date sink to the bottom, and ties (same expiry, or the no-expiry group) fall back to alphabetical. Sorting composes with the existing search and category/location filters. The default list order also changed from Firestore's arbitrary document order to alphabetical by name, which is what the previous order looked like it was trying to be. Pure sort logic lives in `lib/features/inventory/utils/inventory_sort.dart` with six unit tests (alphabetical casing, soonest-first, nulls-last, tie-breaks, input immutability)
- **Default location for inventory items** (WISH-0084). New `UserSettings.defaultInventoryLocation` (null = no default) pre-fills the Location field whenever a new inventory item is created, so adding a batch of kitchen or storage-room items no longer means picking the same location every time. Editable from two places sharing one dialog: a "Default Inventory Location" tile in Settings → Preferences, and a quick-access place icon on the inventory overview AppBar. The dialog offers the known locations (derived from existing items) as one-tap chips plus a free-text field for new rooms; clearing the field removes the default. The pre-fill happens before the discard-changes baseline is captured, so an untouched new-item form still counts as clean. Three unit tests cover the setting's default, toMap/fromMap roundtrip, and copyWith update/clear semantics
- **Transfer quantity** between two inventory items (WISH-0083). A new swap icon opens a transfer dialog from two places: the inventory overview AppBar (pick both items) and an item's own edit page AppBar (source locked to that item, pick only the target and amount). The amount accepts negative values to transfer in the reverse direction, per the wish. The dialog shows each item's current quantity in the pickers, previews the outcome ("Pasta: 5 → 3 · Rice: 1 → 3") once the input is valid, and blocks any transfer that would push either quantity below zero — validated live in the dialog and re-checked authoritatively in `InventoryListNotifier.transferQuantity` against fresh data before the two writes. When transferring from an item's edit page, the form's quantity field is refreshed afterwards so a later Save doesn't write the stale value back, and the discard-changes guard stays honest (clean forms stay clean, dirty forms stay dirty). Pure validation/computation lives in `lib/features/inventory/utils/quantity_transfer.dart` with 9 unit tests covering positive/negative/exact-drain transfers, zero-amount rejection, and both negative-quantity guards
- **Nicknames** (extra search words) on inventory items, catalog items, recipes, and knowledge pages (WISH-0082). Each of the four models gained a nullable `searchAliases` string; every run of whitespace, `,` or `.` in it starts a new alias word, so `soja,soy.sauce` gives three independent search keys. The list searches on all four features now match when the query appears in the title (existing behaviour) *or* in any alias word — with the same `contains` semantics as titles, so partial typing works ("soj" finds alias "soja"). Nicknames are entered via a new "Nicknames" field on each edit page and are deliberately never rendered in list tiles, per the wish. Parsing/matching lives in one shared helper (`lib/utils/search_aliases.dart`: `parseSearchAliases` + `matchesSearchAliases`); the recipe and knowledge autosave snapshots and the inventory unsaved-changes snapshot include the new field so autosave and the discard-changes guard keep working correctly. Old records without the field load cleanly. 14 new tests cover the separator parsing (spaces / commas / periods / mixed runs), case-insensitivity, partial matching, empty-input edge cases, and toMap/fromMap roundtrip + legacy tolerance + clear semantics on all four models
- One-tap "Create subtask" shortcut on the task edit page (WISH-0081). A new AppBar icon (subdirectory-arrow) appears when viewing an existing root task; tapping it opens the new-task form with the parent already selected to the current task, so the user doesn't have to hunt for it in the parent dropdown. The button is intentionally hidden for subtasks since one nesting level is the max (matches the existing constraint). Wired via a new `initialParentTaskId` parameter on `TaskEditPage` and a `?parent=` query string on `/tasks/new`
- "Discard changes?" confirmation on back-navigation from edit pages with unsaved edits (WISH-0079). Built a shared `UnsavedChangesGuard` widget at `lib/presentation/widgets/unsaved_changes_guard.dart` that wraps Flutter's `PopScope` to intercept all back-pop entry points — the AppBar arrow, the Android hardware back button, the iOS edge-swipe gesture, and any programmatic `Navigator.pop` — and only blocks the pop when `isDirty` is true. On confirm-discard it pops the route itself; on cancel the user stays on the page. Wired into the five most data-loss-sensitive edit pages this round: knowledge editor, recipe editor, task editor, inventory editor, and conversation editor. Dirty detection re-uses the existing `recipeAutosaveSnapshot` / `knowledgeAutosaveSnapshot` helpers where they exist; the other three pages compute an inline `_snapshot()` string from the form fields and compare against an `_initialSnapshot` captured after load (or on `initState` for new items). On successful save the snapshot is refreshed before the auto-pop so the guard doesn't double-prompt. The remaining seven edit pages (catalog, calendar event, feedback, contact, asset, transaction, password) follow the same pattern and can be wrapped with a one-line `UnsavedChangesGuard` once dirty-tracking is added
